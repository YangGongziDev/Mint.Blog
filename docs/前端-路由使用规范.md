## 一、Router 总决策

后续 `Mint.Blog.Vue/src/router` 统一按照以下结论执行：

1. `router` 负责页面导航结构，不负责业务数据请求。
2. 路由按“系统路由 + 业务域入口路由”组织，不按页面零散堆放。
3. 布局由路由挂载决定，页面不自行包裹布局组件。
4. 路由守卫统一处理初始化、登录校验、权限校验、标题切换和主题布局切换。
5. 菜单、面包屑、缓存页签等导航派生状态统一由 `route store` 承接，不在页面中重复推导。
6. 路由 `meta` 只描述导航和展示语义，不承接业务数据。
7. 后续新增 `MES` 时，继续沿用同一套路由分层方式，而不是重新发明新的路由体系。

这是本文档的最高原则。后续所有新建页面、新建路由、新增业务域和守卫调整，都必须服从这七条。

## 二、当前 Router 结构

当前 `src/router` 目录结构：

```text
src/router/
  index.ts
  guards.ts
  types.ts
  system.ts
  blog-admin.ts
  blog-surfer.ts
```

统一理解：

- `index.ts` 负责创建路由实例和挂载静态路由
- `guards.ts` 负责统一路由守卫
- `types.ts` 负责路由类型
- `system.ts` 负责登录、异常页、系统页
- `blog-admin.ts` 负责后台业务页面
- `blog-surfer.ts` 负责前台业务页面

这种组织方式是推荐的，因为它是按业务入口拆分，而不是按页面文件分散定义。

## 三、Router 的职责边界

### 1. `router` 负责什么

`router` 负责：

- 路由路径定义
- 页面组件映射
- 布局挂载
- 跳转守卫
- 标题切换
- 登录和权限相关的导航拦截
- 导航状态初始化入口

### 2. `router` 不负责什么

`router` 不负责：

- 页面数据请求
- 表格查询条件
- 表单提交
- 页面业务状态
- 接口返回适配

### 3. 页面不应自己承担路由系统职责

页面不应负责：

- 决定自己挂在哪个布局下
- 自己推导菜单树
- 自己计算面包屑
- 自己处理登录跳转

这些都应由 `router + guards + route store` 统一收口。

- 登录、异常页、通用系统页统一放系统路由文件

### 3. 业务入口路由分开管理

[blog-surfer.ts](file:///Users/yangmufa/UserDevelopment/CSharp/Mint.Blog/Mint.Blog.Vue/src/router/blog-surfer.ts) 负责前台业务页。

统一要求：

- 后台页面路由放后台入口文件
- 前台页面路由放前台入口文件
- 不按页面文件零散注册

## 五、布局挂载规则

### 1. 布局由父级路由决定

当前：

- `/blog-admin` 挂载 [backstage/index.vue](file:///Users/yangmufa/UserDevelopment/CSharp/Mint.Blog/Mint.Blog.Vue/src/layouts/backstage/index.vue)

统一要求：

- 页面属于哪个布局，由父级路由挂载决定
- 页面组件自身不再 import 布局做二次包裹

### 2. 页面选择布局的判断方式

如果页面属于以下场景，挂到 `frontdesk`：

- 内容浏览
- 阅读详情
- 分类归档
- 展示型页面

如果页面属于以下场景，挂到 `backstage`：

- 管理列表
- 编辑页
- 系统配置
- 运营后台

### 3. 未来新增 `MES` 的布局接入

后续如有：

- `/mes-admin`
- `/mes-terminal`

统一先在 `index.ts` 中确定父级入口路由和布局挂载，再拆分对应业务模块路由文件。

不要直接在页面层面自行决定布局。

## 六、路由定义规则

### 1. 路径定义

统一要求：

- 父级入口使用清晰前缀，如 `/blog-admin`、`/blog-surfer`
- 子路由在模块文件中使用相对子路径，如 `article/list`、`article/:id`
- 参数路径使用显式参数名，如 `:id`、`:columnId`

### 2. 路由名称

统一要求：

- 路由 `name` 使用稳定的语义名
- 同一入口下保持统一前缀，例如：
- `blog-admin_article-list`
- `blog-surfer_article_detail`
- `system_user`

路由名应服务于：

- 页签系统
- `activeMenu`
- 跳转和缓存

所以必须稳定、唯一、可读。

### 3. 懒加载

页面组件统一使用动态导入：

```ts
component: () => import('@/views/blog-admin/article-list.vue')
```

统一要求：

- 路由组件默认懒加载
- 不在路由文件中提前静态引入大量页面组件

## 七、Route Meta 规则

### 1. `meta` 负责导航语义

当前常用 `meta` 包括：

- `title`
- `i18nKey`
- `public`
- `blank`
- `hideInMenu`
- `activeMenu`
- `keepAlive`
- `href`

统一要求：

- `meta` 只放导航、展示和访问控制语义
- 不放业务实体数据

### 2. `title` 与 `i18nKey`

统一要求：

- 需要展示标题的页面都应定义 `title`
- 有国际化需求的页面同时定义 `i18nKey`
- 标题切换由守卫统一处理，不在页面内自行设置

### 3. `hideInMenu`

适用场景：

- 详情页
- 创建页
- 编辑页
- 异常页
- 特殊功能页

统一要求：

- 不需要直接出现在菜单中的页面，明确设置 `hideInMenu: true`

### 4. `blank`

适用场景：

- 登录页
- 注册页
- 重置密码页
- 绑定第三方账号页
- 不希望展示布局壳的特殊系统页

统一要求：

- 页面仍然可以挂在某个父级布局入口下，但设置 `meta.blank: true` 后，布局组件只渲染当前页面，不渲染菜单、顶部栏、页签、侧边栏等布局壳。
- `blank` 表示“空白布局渲染模式”，不是“隐藏菜单项”。
- 登录页等认证入口页面应使用 `blank: true`，避免访问 `/system/login` 时显示后台菜单。
- `blank` 应只用于少数特殊页面，不要作为普通业务页面的默认配置。

示例：

```ts
{
  path: 'login/:module(pwd-login|code-login|register|reset-pwd|bind-wechat)?',
  name: 'login',
  component: () => import('@/views/system/login.vue'),
  props: true,
  meta: {
    title: 'login',
    i18nKey: 'route.login',
    public: true,
    hideInMenu: true,
    blank: true
  }
}
```

布局组件需要读取当前子路由的 `meta.blank`：

```ts
const blank = computed(() => props.blank || Boolean(router.currentRoute.value.meta.blank));
```

### 5. `activeMenu`

适用场景：

- 详情页回指列表页
- 编辑页高亮所属资源菜单

统一要求：

- 只在“当前页面不直接出现在菜单中，但需要高亮其归属菜单”时使用

### 6. `keepAlive`

统一要求：

- 只有明确需要缓存的页面才设置
- 不要默认给所有页面加缓存

### 7. `public`

统一要求：

- 明确标注页面是否属于公开访问语义
- 登录页、某些公开页面和系统通用页可标注为公开
- 需要登录后访问的页面由守卫统一拦截

说明：

- 当前项目中 `public` 字段已经参与守卫判断，新建路由时必须按现有守卫语义保持一致，避免出现页面访问边界和守卫逻辑不一致。

## 八、路由守卫规则

### 1. 守卫统一注册

[guards.ts](file:///Users/yangmufa/UserDevelopment/CSharp/Mint.Blog/Mint.Blog.Vue/src/router/guards.ts) 当前统一注册了：

- 进度条守卫
- 文档标题守卫
- 路由初始化与权限守卫

统一要求：

- 新的全局导航规则优先加在 `guards.ts`
- 不要把全局跳转逻辑散在页面中

### 2. 守卫负责的关键流程

当前守卫承担：

- `NProgress` 开始和结束
- 根据目标路径切换主题布局模式
- 初始化 `route store`
- 未登录跳转登录
- 403 判定
- 外链跳转
- 标题更新

这些职责应继续集中在守卫层。

### 3. 页面不重复写守卫逻辑

不推荐页面里到处写：

- `if (!token) router.push('/login')`
- `document.title = ...`
- `if (!hasRole) router.push('/403')`

这类逻辑应统一交给全局守卫。

## 九、Router 与 Store 的边界

### 1. `route store` 承接导航派生状态

[route/index.ts](file:///Users/yangmufa/UserDevelopment/CSharp/Mint.Blog/Mint.Blog.Vue/src/store/modules/admin/system/route/index.ts) 当前承接：

- 动态路由集合
- 菜单树
- 搜索菜单
- 缓存路由
- 面包屑
- 当前入口模块切换

统一要求：

- 路由定义在 `router`
- 路由派生状态放 `route store`

### 2. `auth store` 承接身份状态

[auth/index.ts](file:///Users/yangmufa/UserDevelopment/CSharp/Mint.Blog/Mint.Blog.Vue/src/store/modules/admin/system/auth/index.ts) 负责：

- token
- 用户信息
- 登录状态

统一要求：

- 守卫需要的身份信息统一来自 `auth store`
- 页面不自己复制一套鉴权状态

### 3. 不要在页面内重复推导导航状态

例如：

- 当前激活菜单
- 面包屑数组
- 缓存名称

都应从 `route store` 消费，而不是页面临时再算一次。

## 十、页面接入规则

### 1. 新页面接入 Router 的标准流程

新增页面时，统一按以下顺序操作：

1. 在 `views` 中创建页面组件
2. 判断页面属于前台、后台还是系统页
3. 将路由加到对应模块文件中
4. 配置 `name`、`path`、`meta`
5. 如有需要，配置 `hideInMenu`、`activeMenu`、`keepAlive`
6. 让菜单系统和路由系统通过统一配置联动

### 2. 页面不直接操作路由系统内部结构

页面可以做：

- `router.push`
- 读取 `route.params`
- 读取 `route.query`

页面不应做：

- 动态新增全局路由
- 自己初始化菜单树
- 自己改写全局守卫流程

### 3. 参数页面规则

如：

- `article/edit/:id`
- `article/:id`
- `column/:columnId`

统一要求：

- 参数名语义明确
- 如页面需要直接消费参数，可启用 `props: true`
- 详情页和编辑页通常结合 `hideInMenu` 与 `activeMenu` 使用

## 十一、菜单联动规则

### 1. 菜单不是页面自己决定的

菜单结构统一依赖：

- 路由定义
- 菜单配置
- `route store`

页面不应直接控制自己是否出现在菜单中。

### 2. 路由与菜单要保持一致语义

统一要求：

- 菜单可点击项必须有稳定路由
- 不出现在菜单中的详情页和编辑页，使用 `hideInMenu`
- 需要高亮父菜单时使用 `activeMenu`

### 3. 菜单模块切换按入口切换

当前 `route store` 已按路径区分：

- `admin`
- `surfer`

后续新增 `MES` 时，也应按照业务入口模块切换菜单，而不是混成一套全局菜单。

## 十二、异常页与特殊页规则

### 1. 异常页统一在系统路由中定义

包括：

- `403`
- `404`
- `500`

统一要求：

- 异常页不是某个业务模块页面
- 放在 `system.ts` 统一管理

### 2. 登录页等认证入口使用 `blank`

`/system/login` 挂在 `/system` 父级入口下，而 `/system` 使用 `backstage` 布局。仅设置 `hideInMenu: true` 只能让登录页不出现在菜单中，不能阻止后台布局壳渲染。

因此登录页这类认证入口必须同时设置：

```ts
meta: {
  public: true,
  hideInMenu: true,
  blank: true
}
```

语义区分：

- `hideInMenu: true`：不生成菜单项
- `blank: true`：不显示布局壳，只渲染页面本身
- `public: true`：按当前守卫语义标记公开访问边界

### 3. 外链与 iframe 页

如果页面本质是：

- 外部链接跳转
- 通用 iframe 承载

统一通过系统通用页面或 `meta.href` 处理，不为每个外链页面单独发明一套特殊路由机制。

## 十三、未来新增 MES 怎么做

后续新增 `MES` 时，推荐结构：

```text
src/router/
  index.ts
  guards.ts
  types.ts
  system.ts
  blog-admin.ts
  blog-surfer.ts
  mes-admin.ts
  mes-terminal.ts
```

接入方式：

- 在 `index.ts` 中新增父级入口，如 `/mes-admin`
- 指定其挂载布局
- 再将 `mes-admin.ts` 或 `mes-terminal.ts` 作为子路由并入

原则：

- 先确定入口和布局
- 再拆分业务模块路由
- 不把 `MES` 路由直接塞进 `blog-admin.ts` 或 `system.ts`

## 十四、命名与组织规则

### 1. 文件命名

统一按入口或域命名：

- `blog-admin.ts`
- `blog-surfer.ts`
- `system.ts`

### 2. 路由名称命名

统一使用稳定业务语义名，不用随意缩写，不用临时数字后缀。

推荐：

- `blog-admin_article-list`
- `blog-surfer_archive`
- `system_user-detail`

不推荐：

- `article1`
- `detailPage`
- `tmp-route`

### 3. 类型命名

路由相关类型统一放在 [types.ts](file:///Users/yangmufa/UserDevelopment/CSharp/Mint.Blog/Mint.Blog.Vue/src/router/types.ts) 中维护，例如：

- `RouteKey`
- `AppRouteRecord`

## 十五、禁止项

以下做法不应继续出现在新代码中：

- 页面内部自行包裹布局组件
- 在页面里写全局登录跳转逻辑
- 在页面里写全局标题切换逻辑
- 每个页面自己推导菜单和面包屑
- 按页面文件零散注册全局路由
- 在 `meta` 中塞业务数据对象
- 新增业务域时直接把路由混进现有无关模块文件

## 十六、落地检查清单

每次新增一个页面路由前，先检查：

1. 这个页面属于前台、后台还是系统页
2. 它应该挂在哪个父级布局下
3. 它应该放进哪个模块路由文件
4. `name`、`path`、`meta` 是否清晰稳定
5. 是否需要 `hideInMenu`
6. 是否需要 `blank`
7. 是否需要 `activeMenu`
8. 是否真的需要 `keepAlive`
9. 是否会影响菜单、面包屑或权限守卫

---

## 十七、最终结论

- `router` 负责页面导航结构，不负责业务数据请求
- 路由按系统路由和业务入口路由组织，不按页面零散堆放
- 布局由路由挂载决定，页面不自行包裹布局组件
- 路由守卫统一处理初始化、登录校验、权限校验、标题切换和主题布局切换
- 菜单、面包屑、缓存页签等导航派生状态统一由 `route store` 承接
- 路由 `meta` 只描述导航和展示语义，不承接业务数据
- 后续新增 `MES` 时继续沿用同一套路由分层方式
