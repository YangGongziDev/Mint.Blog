# Mint 认证鉴权规范

## 目的

本文档用于统一 `Mint` 系统的认证、授权、Token、登录态、路由守卫和权限边界规则，适用于当前已有的 `Blog`、`System`，以及未来扩展的 `MES` 等业务域。

本规范只做一件事：

- 让整个系统按照同一套认证鉴权语言长期演进，而不是后端、前端、页面、菜单各自定义一套登录和权限规则。

## 一、认证鉴权总决策

后续认证鉴权统一按照以下结论执行：

1. 认证和授权必须分开设计，不能用一个“权限”概念混在一起表达。
2. 认证负责回答“你是谁”，授权负责回答“你能做什么”。
3. 后端是认证与授权的最终裁决者，前端只做体验优化和界面收口。
4. 登录态统一由 Access Token 驱动，前端不自行发明另一套登录状态来源。
5. 路由权限、菜单权限、按钮权限必须建立在同一份用户身份信息之上。
6. 未登录、Token 失效、无权限三种状态必须明确区分，不能全部混成一个处理分支。
7. 新增业务域如 `MES` 时，沿用同一套认证鉴权结构，不单独发明新协议。

这是本文档的最高原则。后续所有登录、鉴权、路由守卫、权限按钮和 Token 处理，都必须服从这七条。

## 二、核心概念边界

### 1. 认证

认证用于确认身份，回答：

- 当前请求是否已登录
- 当前请求对应哪个用户
- 当前 Token 是否有效

认证结果依赖：

- Access Token
- JWT 签名校验
- Token 过期时间
- 用户基础身份 Claims

### 2. 授权

授权用于确认权限，回答：

- 当前用户是否具有某个角色
- 当前用户是否可以访问某条路由
- 当前用户是否可以点击某个按钮
- 当前用户是否可以调用某个后台接口

授权结果依赖：

- 用户角色
- 用户按钮权限码
- 路由元信息
- 控制器授权标记

### 3. 两者关系

- 没有认证，就没有后续授权
- 认证通过不代表一定有权限
- 前端可做授权预判，但后端必须再次校验

---

## 三、Token 规则

### 1. Token 类型

当前项目主登录态依赖 Access Token。

后续统一要求：

- 认证主凭证统一为 Access Token
- 如果未来增加 Refresh Token，也必须作为明确的第二类令牌，不和 Access Token 混用

### 2. Token 内容

当前 JWT 中包含：

- `sub`
- `unique_name`
- `nameidentifier`
- `name`
- `role`

后续统一要求：

- Token 中只放身份识别和授权判断所需最小信息
- 不在 Token 中放大量业务详情
- 展示型用户信息统一通过用户信息接口获取

### 3. Token 过期

当前过期时间由 `JwtOptions.AccessTokenExpireMinutes` 控制。

统一要求：

- Token 有明确过期时间
- 过期即视为未登录
- 前端收到 `token_expired` 后必须清理登录态并回到登录流程

### 4. Token 存储

当前前端将 Token 存在本地存储 `localStg` 中的 `token` 字段。

统一要求：

- 登录态来源统一使用同一存储键
- 不允许页面层自行缓存另一份 Token
- 清理登录态时统一从同一入口清理

---

## 四、后端认证规则

### 1. 登录接口

当前登录入口：

- `POST /api/system/auth/login`

后续统一要求：

- 登录接口放在 `system/auth`
- 登录成功返回 Access Token 和必要用户标识信息
- 登录失败返回统一错误码，不返回模糊失败文案

### 2. 认证中间件

当前后端流程：

- `UseAuthentication()`
- `UseAuthorization()`

统一要求：

- 所有需要登录的后台接口必须走认证中间件
- 认证中间件负责识别 Token 是否存在、是否合法、是否过期

### 3. 未登录与过期响应

当前 JWT Bearer Challenge 已统一处理：

- Token 过期返回 `token_expired`
- 未登录或无效凭证返回 `unauthorized`

统一要求：

- 未登录和过期必须区分错误码
- 后端不要把两者都返回成同一错误语义

### 4. 匿名接口

允许匿名访问的接口必须显式标注：

- `[AllowAnonymous]`

例如：

- 登录接口
- 博客前台公开查询接口

统一要求：

- 默认后台管理接口按“需要认证”处理
- 匿名能力必须显式声明，不靠约定猜测

---

## 五、后端授权规则

### 1. 角色授权

当前后台接口主要通过：

- `[Authorize(Roles = "Admin")]`

进行角色限制。

统一要求：

- 后台管理类接口优先使用角色授权
- 没有角色要求的后台敏感接口，不允许只靠前端隐藏按钮

### 2. 授权裁决原则

后端必须是最终裁决者：

- 前端菜单隐藏不代表后端放行
- 前端按钮禁用不代表后端放行
- 前端路由不可见不代表后端放行

### 3. 资源级授权

如果未来出现“同角色但只能操作自己的资源”场景：

- 控制器负责接入请求
- 应用层或领域层负责资源归属校验
- 不把资源归属判断全部塞进前端

---

## 六、前端登录态规则

### 1. 登录态唯一来源

当前前端登录态主来源：

- 本地存储中的 `token`

统一要求：

- `isLogin` 必须由 Token 是否存在和是否可用派生
- 不允许页面单独维护 `loggedIn = true` 这类平行状态

### 2. 登录流程

当前主流程：

1. 调登录接口
2. 存储 `accessToken`
3. 拉取当前用户信息
4. 初始化路由和权限
5. 跳转到登录后目标页

后续统一要求：

- 登录成功不等于登录流程结束
- 只有“拿到 Token + 用户信息初始化完成”后，才算完成登录

### 3. 退出登录

统一要求：

- 清理 Token
- 清理用户信息
- 清理动态路由与缓存页签
- 回到登录页或公共入口页

不允许：

- 只删 Token，不重置用户与路由状态

---

## 七、前端路由守卫规则

### 1. 路由守卫职责

前端路由守卫负责：

- 判断是否需要登录
- 判断是否有角色访问权限
- 在未登录时跳登录页
- 在无权限时跳 `403`

### 2. 是否需要登录

当前路由守卫基于：

- `to.meta.public`
- token 是否存在

后续统一要求：

- 公开页面必须显式标注
- 非公开页面默认需要登录

### 3. 角色判断

当前路由守卫基于：

- `to.meta.roles`
- `authStore.userInfo.roles`

后续统一要求：

- 路由角色限制只表达页面访问权限
- 按钮权限与接口权限不混用到路由元信息里

### 4. 未登录跳转

统一要求：

- 未登录访问受保护页面时，必须带 `redirect`
- 登录成功后优先回到原目标页

---

## 八、菜单权限与按钮权限规则

### 1. 菜单权限

菜单权限用于决定：

- 哪些导航项可见
- 哪些页面入口可进入

统一要求：

- 菜单权限建立在角色和路由初始化之上
- 菜单隐藏只做体验控制，不代替后端授权

### 2. 按钮权限

当前前端按钮权限通过：

- `userInfo.buttons`
- `useAuth().hasAuth()`

统一要求：

- 按钮权限码统一由后端下发
- 前端统一通过权限 hook 或权限指令判断
- 页面中不直接散落大量权限字符串判断

### 3. 按钮权限边界

- 按钮权限控制“展示与可操作性”
- 后端接口权限控制“最终可执行性”
- 两者必须同时存在，不能只选其一

---

## 九、401 / 403 / 过期处理规则

### 1. `401 Unauthorized`

适用场景：

- 未登录
- Token 无效
- Token 过期

统一要求：

- 前端收到 `unauthorized` 或 `token_expired` 时，统一重置认证状态
- 清理登录态后回登录页

### 2. `403 Forbidden`

适用场景：

- 已登录
- Token 有效
- 但无访问权限

统一要求：

- 不清理登录态
- 跳转无权限页或提示无权限

### 3. 三种状态不能混淆

必须明确区分：

- 未登录
- 登录已过期
- 已登录但无权限

不允许：

- 全部跳同一个提示
- 全部清空登录态

---

## 十、前后端协作规则

### 1. 后端负责身份真实性

后端负责：

- Token 签名校验
- 过期校验
- 角色校验
- 接口最终放行与拒绝

### 2. 前端负责体验闭环

前端负责：

- 登录页跳转
- 路由拦截
- 菜单显示
- 按钮显隐
- 失效态收口

### 3. 不允许前端替代后端做最终授权

不推荐：

- 因为菜单不可见，就不做后端鉴权
- 因为按钮隐藏了，就不做接口权限校验

---

## 十一、未来扩展规则

### 1. 新增 `MES` 时

后续若新增：

- `mes-admin`
- `mes-terminal`

统一沿用同一套规则：

- 登录仍走统一认证体系
- 角色或终端身份仍走统一授权体系
- 路由守卫、菜单权限、按钮权限仍复用同一模式

### 2. 如果未来引入 Refresh Token

统一要求：

- 单独定义刷新接口
- 单独定义刷新策略
- 不让页面层直接参与刷新细节
- 刷新失败仍回到登录态重建流程

---

## 十二、禁止项

以下做法不应继续出现在新代码中：

- 前端页面自行保存另一份登录状态
- 页面层直接判断 Token 字符串并编写权限逻辑
- 用菜单显隐替代后端授权
- 用按钮禁用替代接口权限校验
- 未登录、过期、无权限三者混为一种错误处理
- 控制器未标鉴权却依赖前端隐藏入口来“防访问”

---

## 十三、落地检查清单

每次新增登录、鉴权或权限控制时，先检查：

1. 这是认证问题，还是授权问题
2. 登录态是否仍只由 Token 驱动
3. 后端接口是否正确标注了 `[Authorize]` 或 `[AllowAnonymous]`
4. 角色权限、菜单权限、按钮权限是否分层清楚
5. 前端是否正确区分了 `401`、`403`、`token_expired`
6. 页面是否把权限判断散落成硬编码字符串
7. 是否错误地让前端承担了最终授权职责

---

## 十四、最终结论

- 认证负责“你是谁”，授权负责“你能做什么”
- 后端是认证与授权的最终裁决者，前端只做体验优化和界面收口
- 登录态统一由 Access Token 驱动，不维护平行登录状态
- 路由权限、菜单权限、按钮权限必须建立在同一份用户身份信息之上
- 未登录、Token 过期、无权限三种状态必须明确区分
- 后续新增 `MES` 或其他业务域时，继续沿用同一套认证鉴权规则
